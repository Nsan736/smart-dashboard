### v0.9.23 で追加したもの(スコープのオブジェクト、景色の範囲の拡張)

- スコープに「オブジェクト」。箱・円柱・円錐・球・角錐・板を組み合わせて作り(大きさ・位置・回転・色・不透明度、数値とドラッグ、元に戻す・やり直し、SceneKit のプレビュー)、地図の長押しで置く。向き・地面からの高さ・倍率・表示を変えられ、地図では足元の輪郭。地面の標高は標高API
- カメラ表示に立体として重ねる(今の Canvas で、遠い面から塗る)。遠いものはリングの印。タップで情報。ほかの表示にも重ねられる
- JSON の書き出し・読み込み(docs/objects-format.md)。Claude API があれば文章から作る
- 景色の範囲を 150/200/300/350km まで(150km以上は確認してから)。遠くはズーム8・7の粗い標高タイルで、山頂は山の一覧の標高で補う。水部は100kmまで
- 上部の切り替えを、横にスクロールできるボタンにした(6つ)

### v0.9.22 で追加したもの(スコープの景色)

- スコープの上部の切り替えに「景色」。層(山・稜線・海と湖と川・地名)ごとにオン・オフ。選んだ層は地点・周辺・経路・電車のカメラ表示にも重ねる
- 山: 国土地理院「日本の主な山岳標高」(1,059件)を同梱。範囲(初期値100km)の中の山を、名前・標高・距離つきの山の形の印で。手前の地形に隠れた山は薄く(設定で隠せる)。文字は3段まで重ならないように。タップで詳細と「地点に登録」
- 稜線: 地理院の標高タイル(ズーム12・10・9)から方角0.5°ごとに計算し、遠い稜線ほど薄く描く。200m動いたか高さが20m変わったときだけ、メインスレッドの外で計算
- 海・湖・川: ベクトルタイル提供実験のズーム8の水部と注記から、見える水面の方角を帯と文字(「東京湾 8km」)で。川と地名も
- 地形と水部のタイルは Wi-Fi などで、画面を開いている間だけ保存(地図タイルと合わせた上限まで)。モバイル通信では保存済みの範囲だけで計算
- 位置のデバッグの仮想の移動で、景色も試せる

### v0.9.21 で追加したもの(スクリプト型の小ツールから、アプリのデータを読む)

- `app.weather` `app.warnings` `app.quakes` `app.pressure` `app.exchange` `app.trains` `app.places` `app.location` `app.sensors` `app.calendar` `app.holidayName()`。アプリがすでに取得・保存しているデータの写しだけで、スクリプトから通信は起きず、書き換えもできない。データが変わったら `onData(kind)`
- ツールの JSON の `permissions` に書いた種類だけを、初めて開いたときに種類ごとに許可する(現在地の緯度経度とセンサーは目立たせ、初めは選ばない)。許可しなかった種類・書いていない種類は null。ツールの画面の「その他」→「データの許可」で変更・取り消し。読み込みの確認の画面とサンプルの一覧にも、使うデータを表示
- センサーは `app.sensors.start("heading")` のように使い始めたときだけ動かし、ツールを閉じたら必ず止める
- 保存する前のプレビューと、文章から作るときの試しの実行では、仮のデータ(`sample: true`)を渡す。Claude への指示に、必要な種類だけを permissions に書くこと、null のときの表示を足した
- サンプル4つ(自分好みの天気、次の電車のカウントダウン、地点を指すコンパス、気圧の小さなグラフ)。「サンプルから追加」にも入れた
- 祝日の名前(`JapaneseHolidays.holidayName`。振替休日・国民の休日を含む)

### v0.9.20 で変えたもの(「撮って聞く」の改善)

- 位置を送らない: 初期値で送るのは画像・質問・方角と向きだけ。地名・緯度経度・周りの地点は初期値でオフ(以前の設定も読み込むときにオフに合わせる)。JPEG に位置などのメタデータがないことをテストで確かめた。答えの下に、送ったものを表示。設定の「送る情報」に、それぞれ何が送られ、居場所が推測できるかを書いた
- Web 検索: Claude API のサーバー側の検索(初期値オン、1回の質問で3回まで)。出典を答えの下に出し、タップで SFSafariViewController。検索の料金(1回0.01ドル)を使用量と月の上限に含める。使えないときは検索なしで聞き直す
- DuckDuckGo の Instant Answer API は、調べた結果(robots.txt がすべて禁止、利用条件のページがない、日本語で結果が出ない、規約に「ほかのサービスの中に表示しない」)を報告し、利用者の判断で使わないことにした
- 場所の特定: 答えの最後の決まった形(<place>)から名前・座標・確からしさ・根拠を読み、撮った方向と合うかを端末の中で確かめる。「地点に登録」で地図で確かめて登録(根拠と出典をメモに残す)
- 小ツールの「サンプルから追加」(examples/tools の11個を同梱)、設定の開発者向けに JavaScript の実行時間の制限の状態

### v0.9.19 で追加したもの(小ツールのスクリプト型)

- JavaScript で動く「スクリプト型」の小ツール(JavaScriptCore)。Canvas 2D に近い描画(1コマ分をまとめて1回で渡し、Swift の Canvas 1枚で描く)、ピクセルの配列からの画像、PNG の書き出し(共有シート)、入力の部品(スライダー・ボタン・切り替え・文字・選択肢)、効果音と単音、振動、ツールごとの保存領域(256KB)、シードつきの乱数、console.log(ツールの画面の「ログ」)
- 専用のスレッドで動かし、2秒以上戻らないと「応答なし」と閉じるボタン。実行時間の制限(非公開の API を dlsym で、利用者の判断で使用)で5秒で打ち切る。実行中に落ちたら、次の起動で「前回このツールの実行中に止まりました」(もう一度試す・無効にする・削除する)。設定の「小ツール」に、すべて止める切り替え
- 読み込みの確認で「スクリプトを含みます」とコード、保存する前のプレビュー。「文章から作る」「文章で直す」でもスクリプト型を作れ、構文と試しの実行で確かめて、エラーがあれば1回だけ作り直す
- サンプル6つ(アナログ時計、跳ねるボール、花火、ドット絵、模様のテクスチャ、的あてゲーム)。予定していたものはすべて入れた(次の版に回したものはない)

### v0.9.17 で追加したもの(スコープの電車の両数と高さ)

- 路線ごとの両数の表(`Resources/railway_cars.json`、[railway-cars.md](railway-cars.md))。22路線を各社の公式サイトで調べた(出典のURLと確認日つき)。千代田線の綾瀬〜北綾瀬だけの列車は3両。混在して見分けられない路線と、公式で確かめられない路線は「両数は目安」。設定の「路線ごとの両数」で上書きできる(初期値は表の値)
- 線路の高さ: 同梱の線路の形に、25mごとの地面の標高(地理院タイルの標高タイル)と、区間の種類(国土地理院ベクトルタイル提供実験の鉄道中心線の railState)を足した。線路の高さ = 地面 + 高架 +8m / 地下 −15m(設定で変更可)
- カメラ表示の電車の箱を、線路の高さに置く(自分の高さとの差で上下が変わる)。地下の区間の車両は半透明の破線の輪郭だけ。印の文字に高低差(「350m ↑8m」「地下 ↓15m」)、データがなければ「高さは目安」
- 移動タブの列車の詳細に、今の区間(高架・地上・地下・不明)と両数
- 調べた結果(OSM・地理院タイル・ベクトルタイルの比較、データの増加)は、下の「設計判断」と「外部データの注意点」

### v0.9.16 で追加したもの(スコープの電車)

### v0.9.15 で追加したもの(スコープの地点の表示・非表示と高さ)

- 地点の表示・非表示(削除せずに隠す)。一覧の目のボタン、「すべて表示」「すべて非表示」、「表示中だけ/すべて」の絞り込み。非表示の地点はカメラ表示・コンパス表示・地図・ホームの「一番近い地点」から外す。ピン留めした地点は非表示でもカードに出し「非表示中」と添える。「選んだ1つ」は非表示の地点も選べる
- 地点の高さ(標高+地面からの高さ)。標高は国土地理院の標高APIで、登録したときに自動で取得(海上などは「データなし」で未設定)。保存済みの地点は未設定として引き継ぎ、Wi-Fi接続中に自動で取得。編集画面で手入力・再取得・地面からの高さ
- 自分の高さ(「地面の標高+手の高さ」が初期値。100m以上動いたときだけ標高を取り直す。取れないときはGPSの高度)。カメラ表示の印の上下の位置を仰角で決め(地球の丸みと大気の屈折の補正つき)、印の下・コンパス表示・一覧に高低差

### v0.9.14 で追加したもの(駅と路線の検索)

- 検出した事業者すべての駅と路線を、端末に保存した駅の一覧だけで検索する(駅名・路線名・英語名・読み仮名・駅ナンバリング・ODPT の ID。ひらがな/カタカナ・全角/半角・大文字/小文字を区別しない)。同じ名前の駅を1行にまとめ、路線ごとの駅に色・事業者名・駅ナンバリング
- 使う場所: 路線の登録(駅から路線と方面を直接登録)、行きたい駅の選択(以前の駅名の検索を置き換え)、移動タブの地図(虫めがねのボタン。選んだ駅へ地図を動かして駅の情報)。最近検索した駅を5件
- 駅の一覧: 事業者10件ずつまとめて取得し、事業者ごとに30日保存。Wi-Fi接続中は検出のあとと検索の画面を開いたときに自動、モバイル通信ではボタン。取得は約48KB(gzip、7事業者・約440駅、2回の通信。都営は公開エンドポイントなので別の1回)、保存は約0.3MB(都営149駅の実測で1駅あたり約0.7KB からの見積もり)
- 読み仮名は、東京メトロの駅名にだけ ja-Hrkt がある(ほかの事業者は ja と en だけ)。同じ名前の駅をまとめるので、「しんじゅく」で都営の新宿も出る。東京メトロ以外だけの駅(例: 都営の西馬込)は、かなでは探せない(漢字・英語名・駅ナンバリングで探す)

### v0.9.13 で直したもの(検出が HTTP 400 で止まる不具合)

- v0.9.12 の検出は、実機とトークンで odpt:Railway が HTTP 400「too many OR condition in odpt:operator」になり、検出できなかった(事業者34件をカンマ区切りで並べていた。上限は10件)。そのあとの問い合わせは、絞り込みが空のまま送られて0件になっていた
- 路線の一覧は絞り込まずに全件を1回で取る。ほかのカンマ区切りの問い合わせ(検出、運行情報、遅れ、駅名の引き当て)は、すべて10件ずつに分ける(`ODPTQuery.chunks`)。値がなければ問い合わせない
- 失敗したら、その段階で中止し、「◯◯が取れなかったため、検出を中止しました」と、URL(トークンを除く)・応答の本文を表示する
- 駅名の引き当て(行先の駅名)も、10件を超えると 400 になり、黙って駅IDの末尾の表示になっていた(v0.9.12 以前から)。同じ修正で直る

### v0.9.12 で追加したもの(ODPTの事業者の自動検出)

- 登録の画面を「事業者(使えるデータのラベル)→ 路線(色、検索)→ 駅と方面」に。時刻表のない路線は「運行情報のみ登録」
- 既存の機能(地図・路線図・列車の位置・遅れ・乗車中の判定・駅に重ねる電車・駅の時刻表・経路の検索・デバッグ)は、事業者に依存しない作りのまま、検出した事業者の路線にも広がる。事業者をまたぐ経路のため、駅の一覧に、列車ごとの時刻表がある検出済みの事業者の駅を入れる
- 線路の形に、東京メトロ10路線・横浜市営地下鉄2路線・つくばエクスプレス・りんかい線・多摩モノレール・ゆりかもめを追加(N02 の駅で作成。22路線、約45KB)
- check_local.py で、フィクスチャのトークンらしき文字列と、Git の管理下のファイルの acl:consumerKey の値、private/ が管理外かを確かめる

## 実装済みの機能(1行ずつ)

- ホーム: 各機能の要約のカード。並べ替えと表示・非表示(非表示のカードのデータは取得せず、センサーも動かさない)
- 天気: Open-Meteo(現在、24時間、7日、日の出入り、UV)。現在地の地名。1リクエスト
- 雨の要約: 0〜60分は気象庁のナウキャスト、その先は予報モデル
- 雨雲レーダー: 気象庁のナウキャストのタイルを地図に重ねる(専用画面でだけ通信)
- 警報・注意報: 気象庁の新形式(r8)。市区町村は同梱の表で決定。ホームと天気タブ
- 地震: P2P地震情報。一覧、ホームのカード、詳細画面(津波、震源までの方角と距離、地図、各地の震度)
- 観測点ごとの震度の地図: 気象庁の観測点の一覧を同梱し、1枚の重ね描きで色分け
- 気圧: 実測(5分ごと、7日保存)と予報を1本の線に。ホームのカード、天気タブの節、詳細画面(過去4日〜16日先、Canvas の自前描画、タップで値)
- バックグラウンドでの気圧の記録(オプション、無音のオーディオ)
- 為替: 日次レート(JPY基準)と、オフラインの換算
- 移動(v0.9.9 で電車タブから作り直し): 地図中心の3段の画面(切り替え/地図・路線図・記録/情報と設定)。運行情報、駅の時刻表(手動で一度だけ保存)、路線の地図と路線図、時刻表から計算した列車位置と、リアルタイムの遅れ。v0.9.12 から、トークンで使える事業者を自動で検出して広げる

## コードを読んだだけでは分からない設計判断と、その理由

- **オブジェクトは今の Canvas で面を塗る**(v0.9.23): SceneKit をカメラの向きと画角に合わせて重ねる方法と比べた。SceneKit は深度バッファで面の前後が正確になり、面の数が多くても強いが、カメラの映像の上に透明の SCNView をもう1枚重ねることになり(描く層が増え、SceneKit の描画のループとメモリ(数十MB)が足される)、毎コマ端末の向き・画角・地球の丸みをカメラに写す必要がある。半透明の面の重なりは SceneKit でも並べ替えが要る。このアプリのオブジェクトは形が少なく(丸い形も12角形・経度10×緯度6に減らし、1つで数十〜数百面)、電車の車両の箱と同じ投影と画家のアルゴリズムで足り、景色・電車・地点と1枚の Canvas にまとまるので、iPhone SE 第2世代ではこちらが軽いと判断した(実機では未計測)。面の数は1コマ2,000まで、遠いものは印にする。面どうしが交わる形では前後が崩れることがある(画家のアルゴリズムの限界)
- **景色の遠くは粗いタイルと山頂の補いで**(v0.9.23): 100km より遠くをズーム9で取ると、350kmで数十MBになる。ズーム8(約500m)・7(約1km)にすると、350kmでも1か所4〜6.5MB(実測)。粗いタイルでは山頂が低く出る(富士山はズーム9で約3,690m)ので、山の一覧の山頂を円すいとして足す。水部は遠くでは地平線の下になることが多いので100kmまで
- **景色の山は「日本の主な山岳標高」だけを使う**(v0.9.22、利用者の判断): ベクトルタイルの山名の注記は件数が多いが、位置が文字の置き場所(山頂から0.7〜4kmずれる)で標高もない。範囲の初期値は100km(50kmだと東京駅から一覧の山が2つだけで、富士山が入らない)
- **稜線は端末で計算する**(v0.9.22): 方角0.5°ごと・距離の1.2%ずつで、半径100kmで約29万点。標高タイルは近くを細かく(ズーム12)、遠くを粗く(ズーム9)にして、1か所2.6〜4.6MBに抑えた。東京タワーの高さから、富士山が方角250.5°・仰角1.6°・97.6kmに出ることを Python で確かめた。OpenStreetMap(山頂・水部)は ODbL の条件が同梱・保存したデータにかかるので使わない
- **水面はベクトルタイルの面を格子に塗って調べる**(v0.9.22): 方角ごとの道のりで点が水面の中かを毎回多角形で調べると重いので、ズーム8のタイルを1枚512×512のます目に塗っておく(1か所で最大約1,500×1,500)。海はタイルの境目で切れているので、隣り合う水面をまとめてから名前を付ける。海は1つにつながるので、帯の名前は区域の中で一番近い注記にする
- **スクリプトには、アプリのデータを JSON の文字列の写しで渡す**(v0.9.21): JavaScriptCore のスレッドからアプリの状態(MainActor)を直接読ませると、スレッドをまたぐうえ、スクリプトが取得の関数を呼べてしまう。画面の側で許可した種類だけを JSON にして、コマの前に渡すだけにした。スクリプトの側は読むたびに JSON.parse するので、写しを書き換えてもアプリには影響しない。変わったかは5秒ごとに作り直して文字列で比べる(観測の仕組みを使わないので、どのデータも同じ作りで済む)。列車の位置は時刻で動くので、5秒ごとに変わる
- **location.coarse と location.precise を分ける**(v0.9.21、利用者の指定): 天気・警報・地震・地点の中にも居場所が分かる項目(地点名、地域、緯度経度)があるので、それぞれ location の許可がなければ null にする。天気の数値・地点の方角と距離だけでは、居場所はほぼ分からない
- **「撮って聞く」は、居場所が推測できる情報を初期値で送らない**(v0.9.20、利用者の指定): 写っているものから見つけるのが基本。自分の位置は、答えの場所の照合のために端末の中でだけ使う。以前の設定は `ClaudeSettings.privacyVersion` が2より小さいとき、読み込みでオフに合わせる(利用者が新しい版で選び直した設定は、そのまま)
- **Web 検索は基本の版(web_search_20250305)を使う**(v0.9.20): 動的な絞り込みの版(20260209 以降)はコード実行を使い、プログラムからのツールの呼び出しに対応しないモデルでは allowed_callers: ["direct"] が必要になる。基本の版は直接呼ぶだけで、ZDR の対象でもある。Claude Haiku 5.5 で使えるかは公式のドキュメントに明記がなく(Models API の capabilities.server_tools.web_search.supported で分かる)、使えずに 400 になったら検索なしで聞き直す
- **場所は、答えの最後の決まった形で返してもらう**(v0.9.20): JSON の出力の機能(structured outputs)を使うと、答えの文と一緒に扱いにくい。<place>…</place> の中の JSON を読み、読めなければ特定できないとして扱う。座標は作らせない(特定できないときは identified: false)
- **スクリプト型は JavaScriptCore の JIT なし(インタープリター)で動く前提で軽くする**(v0.9.19): アプリの JavaScriptCore では JIT が使えないため、1コマの計算と描画の命令を少なくする。描画の命令は JavaScript の側で数の配列にまとめ、1コマに1回だけアプリが読む(命令ごとにアプリを呼ぶと、JavaScript とアプリの行き来が重い)。描く側も Canvas 1枚。初期値は1秒30コマ
- **スクリプト型は、毎コマ描き直す方式にした**(v0.9.19): ブラウザの Canvas のように前の絵が残る方式だと、画像を毎コマ持ち続ける必要があり、メモリと書き出しが重くなる。描いた命令のリストを毎コマ置き換える。前の絵を残したいツールは、image.update で自分の画像に描いて drawImage する
- **実行時間の制限は非公開の API を使う**(v0.9.19、利用者の判断): JSContextGroupSetExecutionTimeLimit は iOS の JavaScriptCore に実体があるが(SDK の JavaScriptCore.tbd に記号がある)、公開のヘッダーにない。App Store に出さない配布なので審査の問題はないが、将来の iOS で消える・動きが変わる可能性がある。dlsym で探し、見つからなければ使わない(固まったスクリプトは止められず、閉じたあともスレッドが CPU を使い続けるが、アプリを終了すれば戻る)
- **実行中の記録は、バックグラウンドに回ったときにも消す**(v0.9.19): 利用者がアプリの切り替え画面でアプリを終了したときに「前回止まりました」と誤って出さないため。フォアグラウンドに戻ったら書き直す
- **Claude API はストリーミングを使わず、1回の応答を待つ**(v0.9.18): 答えを一度に表示する画面なので、待つ時間を180秒にして、待っている間は「考え中…」と取り消しのボタンを出す。最大の出力は小ツール16,000、カメラ8,000トークン(思考を含む)。ドキュメントでは、10分を超える長い依頼にはストリーミングを勧めているが、この2機能では届かない
- **思考のブロックは送り返さない**(v0.9.18): ツールを使わない会話では不要(ドキュメント)。送り返すと、会話の途中を変えたとき(続けての質問で古いやり取りを落とすとき)に、思考のブロックの署名が合わず 400 になることがある。作り直しの依頼と続けての質問では、前の答えの文章だけを送る
- **「撮って聞く」は写真の撮影(AVCapturePhotoOutput)ではなく、映像の1コマを使う**(v0.9.18): 日本の iPhone は写真の撮影でシャッター音が鳴る。映像のコマなら鳴らず、押した瞬間の映像がすぐ取れる(画質は1280×720の映像のまま)。見えていた範囲だけを切り出すので、画面の縦横比のまま送る
- **プロンプトキャッシュは、毎回同じになる部分の終わりに目印を付ける**(v0.9.18): 小ツールは system prompt(形式の説明、約3,000トークン)。カメラは、画像と撮影の状況の文まで。続けて質問するとき、古いやり取りを落としても、最初のメッセージの画像と状況は同じなので、キャッシュから読める(読み込みは入力の1/10の料金)。初回の書き込みは入力の1.25倍
- **月の上限は、呼び出す前に確かめる**(v0.9.18): 呼び出しの途中では止められないので、上限をわずかに超えることがある。金額は、呼び出したときの料金の設定で計算して記録する(あとで料金を変えても、過去の分は変わらない)
- **ヒアドキュメントでパッチを当てない**(v0.9.17 の ci の失敗の原因): この環境(Git Bash のツール)では、ヒアドキュメントの中のバックスラッシュ2つが1つになることがある。Swift の文字列の改行の記号が本物の改行になり、ビルドが通らなかった。バックスラッシュを含む変更は、Edit ツールか、ファイルに書いたパッチで行う。check_local.py が、行の途中で切れた文字列を見つける

- **名前を変えても、内部の値は変えない**: `AppTab.waypoint`、`HomeCardKind.waypoint`、`waypoints.json`、型 `Waypoint`、設定キー `waypoint.showsHeading` は、表示名が「スコープ」「地点」になったあとも以前のまま。保存済みのデータと設定を引き継ぐため。同じ理由で、以前の「タイマー」のタブは、保存済みの並びの中で「小ツール」に読み替える
- **気圧の詳細画面と、観測点の地図は、あえて標準の部品を使っていない**: Swift Charts と MapKit のピンは、部品の数が数千になると iPhone SE 第2世代で重かった(実機の報告)。1枚の Canvas / 1枚の重ね描きで描き、スクロール中は描き直さない。スクロール位置を View の状態に入れないのも同じ理由
- **列車の位置は、リアルタイムの在線位置を使わず、時刻表から計算する**: 利用者の指定。リアルタイムのデータから使うのは遅れ(秒)だけ
- **カメラ越しの表示は ARKit を使わない**: 利用者の指定。回転行列から画面上の位置を計算する。ARで道路に帯を描く案は、調査のうえで見送り(記録は private/ideas.md)。経路は地図の案内が中心
- **カメラのセッションはアプリ全体で1つを使い回す**: 画面ごとに作り直すと、開くたびに設定のやり直しで遅かった
- **気圧の予報の補正は、全体を同じ量だけずらす**: 予報は地表の気圧で、端末のある高さとの差はほぼ一定だから。50km以上離れた地点に変わったら、保存した予報を捨てる(別の地点の値とはつなげない)
- **過去の気圧を100日分持つ案はやめた**: 利用者が見たいのは予報。過去は4日分の表示、7日分の保存に縮小した(Historical Forecast API も使わなくなった)
- **線路の形は、OpenStreetMap ではなく国土数値情報(N02)を使う**: N02 は国の公開データで、2020年度以降の版は CC BY 4.0(出典の表記と、加工したことの明記で、加工・同梱できる)。1路線が1本の中心線で、運営会社と路線名の属性があるので、ODPT の路線と対応付けやすい。OpenStreetMap(ODbL)は線路の本数ごとに線が分かれ、1本にまとめる手間が大きく、抜き出したデータを同梱すると、その部分を ODbL で公開する義務(継承)が生じうる。N02 の精度は2万5千分の1の地図が元で、駅とのずれは都営でおおむね数m〜数十m(一番大きいのは大江戸線の最初の都庁前で約70m)
- **移動タブの画面は、List の中に地図を置き、切り替えのボタンは List の外(上)に置く**: 固定の見出しを List の中で作ると insetGrouped では上端に残らないため。List の中の地図は、画面の外に出ると作り直されることがあるので、表示範囲を覚えて開き直す
- **駅を線路に合わせるときは「谷」のうち一番手前を選ぶ**(`GeoPath.snap`): 駅の順に、前の駅より先の区間で、線に沿って近づいて離れる所(谷)を候補にし、一番近い谷から100m以内のうち一番手前のもの。単に一番近い点を選ぶと、大江戸線の環状部のように線が近くを2回通る所で先へ飛び、その後の駅がすべてずれた(作るときに実際に起きた)。谷に絞らないと、直線の区間でも手前の点を選んでしまう。スクリプト(`check_stations`)とアプリで同じ規則にしてある
- **路線の線は TrainStore で1か所で作り置きする**(`rideLines()` / `rideLine(for:)`): 地図の線、列車の位置、判定、デバッグ、経路の線で同じ線を使わないと、列車が線路から外れて見えたり、判定の位置と地図がずれたりするため
- **地図は北が上のままで、回転させない(移動タブ)**: 列車の矢印の向きを、地図の回転に合わせて直していないため。回転を入れるなら、`TrainAnnotationView` の向きから地図の向きを引く必要がある
- **地図に触れている間は外側の List のスクロールを止める**(`ParentScrollLockRecognizer`): MKMapView を List の行に入れると、縦になぞったときに地図と画面のどちらが動くかが定まらない。自分では何も認識しない(ほかのジェスチャーの邪魔をしない)認識器で、触れたときに止め、離れたら戻す
- **列車の運行のIDは、列車番号・カレンダー・運行日で作る**(`TrainPositionCalculator.tripID`): 列車番号は毎日同じなので、番号だけでは日をまたぐと別の運行と区別できない。経路の区間(`JourneyLeg.tripID`)と、時刻表から計算した列車の位置(`TrainPosition.id`)を同じ形にして、「予定どおり」を比べる
- **駅の時刻表は odpt:StationTimetable ではなく、保存した列車ごとの時刻表から作る**: 登録していない駅でも、追加の通信なしで出せるため。遅れ(列車番号→秒)は、列車番号が毎日同じなので、今の前後3時間の電車にだけ反映する
- **経路の検索は6時間以内、乗り換えは3回まで**: 深夜に探したときに始発まで届くように6時間にした(0時半に探すと、6時半までの電車)。乗り換えの時間は設定の値に、150mより離れた駅どうし(蔵前、三田など)は歩く時間を足す
- **経路の最初の電車の「間に合う」は、出発の駅が現在地から3km以内のときだけ**: それより遠い駅は、今そこへ向かう前提ではない(予定を調べているだけ)と考え、今の時刻から探す。3km以内なら、急いで駅に着ける時刻から探す
- **経路の検索のために足した路線は、登録した路線とは別に持つ**(`TrainStore.routeRailways`): 運行情報や駅の登録を増やさず、地図の線と列車ごとの時刻表だけを保存する。設定の「経路の検索用の路線」で消せる
- **降りる駅の通知は、移動タブを表示している間だけ**: 位置の記録と判定がフォアグラウンドだけなので(バックグラウンドの位置情報は使わない)
- **経路の検索は、保存した時刻表だけで行い、外部の経路検索APIを使わない**: 通信量を最小にする方針のため。使えるのは列車ごとの時刻表がある事業者の路線だけ。v0.9.12 から、検出した事業者の駅も駅の一覧に入れて、事業者をまたいで探す
- **事業者の検出は、データを丸ごと取らず、確かめるための最小の問い合わせにする**(v0.9.12): 列車ごとの時刻表は1路線で100KBを超えるので、「列車のIDを1つ得て、その列車の時刻表を1件だけ取る」で有無を確かめる。列車のIDは、走っている列車(odpt:Train)か、駅時刻表1つから得る。駅時刻表の有無と駅の位置は、各路線の最初の駅の odpt:Station だけで分かる。どの問い合わせも、複数の事業者・IDをカンマ区切りで1回にまとめる
- **遅れが取れるかは、昼間に列車が1本もない事業者だけ「なし」と判断する**: 深夜は走っていないだけのことがあるので、未確認にして、遅れの取得を試す(取得の結果で「なし」になる)
- **チャレンジ限定の事業者は、コードの一覧(`OperatorCatalog.challengeOnly`)で外す**: ckan.odpt.org の API は公開されていない(/api/3/action は /dataset にリダイレクトされる)ので、アプリがライセンスを調べることはできない。ライセンスが変わったら一覧を直す
- **スコープの電車は、近い8本だけを形で描く**(v0.9.16): 1本10両で、車両ごとに8つの角の投影と最大3面の塗りがあり、20本すべてを形にすると1フレームで数百の面になる。SE2 で30fpsを保つため、形は近い8本・600m以内に絞り、ほかはリングの印にした。実機で重ければ、`ScopeTrainRenderer.maxShapeTrains` と `shapeDistance` を下げる
- **スコープの電車の車両は、線路の高さに置く**(v0.9.17。v0.9.16 は地面に置いていた): 線路の高さ = 線路の下の地面の標高 + 区間ごとの値(高架 +8m、地下 −15m)。線路の高さか自分の高さが分からなければ、地面(自分の高さ − 手の高さ)に置き「高さは目安」。地下鉄の路線でも、地下と分かっている列車には「地下鉄」と添えない(「地下 ↓15m」で分かるため)
- **線路の高さのデータは、地理院の標高タイルとベクトルタイル提供実験を使い、OSM は使わない**(v0.9.17): 調べた結果、(1) 地理院タイルの標高タイル: DEM5A(航空レーザー、精度0.3m以内、地面の点から作るので高架の下の地面の高さ)、DEM5B(写真測量、0.7m)、DEM10B(5m)。z15 の5mメッシュで、線路の点ごとに引ける。(2) 地理院ベクトルタイル提供実験の鉄道中心線に railState(通常部、橋・高架、トンネル、地下、雪覆い、運休中など)がある。試験公開で測量成果ではないが、国土地理院コンテンツ利用規約(PDL 1.0 準拠)で、出典と加工の明記で使える。(3) OSM の bridge/tunnel/layer は細かいが、ODbL で、同梱するデータ(抽出したもの)に継承の条件(同じライセンスでの提供)がかかる。アプリの同梱データを ODbL にしたくないので使わない。(4) 高架の高さ・地下の深さのデータは見つからない(N02 にもない)ので、区間ごとの目安の値を設定に置いた
- **高さは25mごとにした**(v0.9.17): 車両の長さ(20m)に近く、データは圧縮後 +24KB。10mにすると約2.5倍になる。区間の切り替わりは25m以内の誤差がある(銀座線の渋谷のような短い高架は拾えない)
- **両数は公式で確かめた値だけを表にし、見分けられない路線は「目安」と出す**(v0.9.17): ODPT のデータに両数はなく(odpt:carComposition は全事業者でなし)、列車番号の末尾の文字の意味は公式で確かめられない。三田線は公式の駅時刻表に6両の印があるという情報もあるが、交通局のサイトはボット確認(CAPTCHA)で自動では開けなかった。表を直すときは JSON と docs/railway-cars.md の両方
- **スコープの電車の位置は1秒ごとに計算し、描くときは速さで先へ進める**(v0.9.16): 列車の位置の計算は時刻表の全列車を見るので、描くたび(30fps)には行わない。前の計算との差から線に沿った速さを出し、最大1.5秒だけ先へ進める(止まっている列車、区間が変わって飛んだ列車は進めない)
- **地球の丸みの補正は、距離²÷(2R) に (1 − 0.13) をかける**(v0.9.15): 依頼では「屈折の補正(係数0.13程度)をかける」。屈折は光を地面のほうへ曲げ、丸みによる見かけの低下を小さくするので、係数そのものではなく (1 − 係数) をかけるのが測量で使う形(見かけの低下 ≈ 0.0683 × 距離km² m)。10kmで約7m、100kmで約683m
- **地点の標高の「データなし」は自動で取り直さない**(v0.9.15): 海上などは何度取っても同じなので、Wi-Fiのたびに問い合わせない。編集画面の再取得か手入力で直す
- **自分の高さの「地面の標高」は、100m以上動いたときだけ取り直す**(v0.9.15): 依頼の指定。1回約70バイトでも、カメラ表示の間は位置が数秒ごとに変わるので、距離で絞る。最後の値は UserDefaults に保存し、開き直しても近くなら使う
- **駅の検索は、同じ名前の駅を名前だけでまとめる**(v0.9.14): 経路の検索の駅のまとまり(`TransitDirectory.groups`)は乗り換えの関係で作るが、検索では、乗り換えの情報がない事業者の駅も含めて「新宿」を1行にしたいので、正規化した名前が同じなら同じ行にする。遠く離れた同じ名前の駅も1行になる(下に路線ごとに並ぶので区別できる)
- **検索の駅の一覧は、経路の検索の駅の一覧と同じ保存を使う**(v0.9.14): 同じ odpt:Station を2回取らないため。キーを operatorStations2 に変えたので、v0.9.14 に上げたあと1回だけ取り直す
- **検出の結果は、キャッシュの削除では消さない**: 登録した路線の事業者のエンドポイントや、使えるデータを引くのに使うため。見つからない事業者は、トークンが必要な事業者として扱う(`OperatorDirectory.resolve`)
- **トークンがないとき・無効なときも、公開エンドポイントで検出する**: 都営は公開エンドポイントのまま使う(上書きの定義)。公開エンドポイントに事業者が増えても、コードを変えずに出る
- **線路の形の、N02 の駅で作るモード**: 開発側にはトークンがないので、トークンが必要な事業者は N02 の駅だけで線を作った。線の向きは駅の順と合わないことがあるので、アプリが最初と最後の駅の位置で向きをそろえる(`RideLine.oriented`)
- **乗り換えは odpt:connectingStation を使う**: 駅IDまで分かり、名前の違う乗り換え(東日本橋と馬喰横山、西巣鴨と新庚申塚)も取れる。都営では、同じ名前の都営の駅どうしはすべて書かれていた(2026-09-28に確認)。書かれていない事業者のために、同じ名前で500m以内の駅も乗り換えとみなす
- **経路は、着く時刻を変えずに途中の列車をできるだけ遅くする**: 接続を順に調べる方式は、同じ時刻に着く経路のうち、最初に見つかった(早く出る)ものを返すため。乗り換えで長く待つ経路になりやすい
- **駅に重ねる電車は、アノテーションではなく1枚の重ね描き**: 数が多いときに iPhone SE 第2世代で重くならないように。タップは部品に頼らず、アイコンの位置を計算して判定する
- **経路の検索のために足した路線の遅れは取らない**: 遅れの取得は、登録した路線だけ(`TrainStore.registeredRailways`)。足した路線は時刻表どおりとして扱う(通信量を増やさないため)
- **乗車中の判定は、時刻表の列車との照合で行い、リアルタイムの在線位置は使わない**: 列車の位置と同じ方針。判定のための通信はない
- **移動の記録はバックグラウンドで続けない**: 位置のバックグラウンドモードは、LiveContainer で Info.plist が効かないときに allowsBackgroundLocationUpdates を設定すると例外で落ちるため。気圧の無音再生でアプリが起きていても、フォアグラウンドの許可(使用中のみ)だけでは位置の更新は止まる
- **並行する道路の対策は、駅以外での停止と、線までの距離**: 速さだけでは電車と車を区別できない。止まる場所(駅かどうか)が一番の手がかりで、駅以外で25秒以上止まったら判定をやり直し、次は駅での停止を見るまで判定を出さない。信号の少ない道路を止まらずに走る車は、線に近ければ「確からしさ 低」で判定が出ることがある
- **デバッグの仮想の移動は記録に残さない**: 実際の移動の記録と取り違えないため。仮想の移動の間は、実際の現在地を地図に出さず、上部に赤い帯を出す
- **トーナメント表は、試合ごとの部品を作らず、1枚の Canvas に描く**: 64人で63試合・126個のボタンになるのを避けるため(気圧のグラフ、観測点の地図と同じ考え方)。タップは配置のロジックから判定する。Canvas の中では文字の省略(lineLimit)が使えないので、名前は文字の幅(全角2、半角1)で切る
- **メトロノームは、オーディオのセッションを非アクティブにしない**: 気圧の無音再生と同じセッションを共有しているので、止めるときに非アクティブにすると、無音再生まで止まる
- **割り勘・割引・消費税は、先に小数第3位で丸めてから円未満を処理する**: 2進数の誤差で1円ずれるのを防ぐため
- **Open-Meteo に models=jma_seamless を指定しない**: 指定すると降水確率と UV が null になる
- **JSONのツールは、プログラムを実行しない形式にした**: 他人が作ったものを読み込む前提なので、通信や端末のデータに触れる項目を形式に持たせず、式も専用の評価器(上限つき)で処理する
- **テストしたいロジックは View の外に置く**: View に準拠した型は全体が `@MainActor` になり、テストから呼びにくい。`@MainActor` なクラスの静的メンバーも同じ(`nonisolated static` にするか、定数を別の enum に出す)
- **ファイルのパッチは、Pythonのスクリプトをファイルに書いてから実行する**: bash のヒアドキュメントに Swift や JSON の文字列を入れると、引用符やバックスラッシュで壊れることがある(上の「ヒアドキュメントでパッチを当てない」)。Swift のファイルを直接書くときは、`\(` や `\.` のバックスラッシュを二重にしない(check_local.py が検出する)
- **ドキュメントの更新は ci の前に同じ push に入れ、ci が成功したコミットにタグを付ける**: release.yml はテストをしないため

| 気象庁 警報・注意報 | 公式のAPIではない。以前の `data/warning/{コード}.json` は 2026-05-28 で更新が止まった。今は `data/r8/{府県予報区}.json`。コードと名称の表は、警報ページのスクリプトから写したもの(`WarningCatalog`)。河川の氾濫は別ファイルで、未対応。1つの市が複数の区域に分かれている所(約40市町)は、全区域をまとめて表示 |
| 気象庁 地域の表(`Resources/jma_areas.json`) | area.json から市区町村と府県予報区だけを抜いて同梱。市町村合併などで古くなったら、`python scripts/update_jma_areas.py` で作り直してコミットする(2026-09-28に、今の同梱ファイルと同じ内容になることを確認) |

## 作業の進め方(要点)

- 詳細は CLAUDE.md の「ビルドと検証」。push と ci は区切りごとに1回だけ(`gh workflow run ci.yml --ref main`)。その前に `python scripts/check_local.py` を通す
- ci は通常4〜5分。**v0.9.7 で約11分、v0.9.11 で約16分かかった(原因は未特定)**。v0.9.7 のときは、テスト自体はミリ秒、実機向けのコンパイルは51秒で、長かったのはシミュレーターでのビルドとテストの段階。v0.9.11 もその段階(「ビルドとテスト(iOSシミュレーター)」)で長かった。どちらも失敗はしていない。調べるなら、ci のログでシミュレーターの起動とビルドの各段階の時刻を比べる(macOS の runner の混み具合、シミュレーターの起動待ち、ビルドのキャッシュがないこと、などが候補)。調べるための ci の実行も回数に数える
- リリース後は、apps.json が main に反映されたことを確かめる(`git show origin/main:apps.json`)。raw のURLは最大5分キャッシュされる
- `private/` は `.git/info/exclude` で管理外にしてある(クローンし直したら、同じ1行を足す)
