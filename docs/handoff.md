### v0.9.13 で直したもの(検出が HTTP 400 で止まる不具合)

- v0.9.12 の検出は、実機とトークンで odpt:Railway が HTTP 400「too many OR condition in odpt:operator」になり、検出できなかった(事業者34件をカンマ区切りで並べていた。上限は10件)。そのあとの問い合わせは、絞り込みが空のまま送られて0件になっていた
- 路線の一覧は絞り込まずに全件を1回で取る。ほかのカンマ区切りの問い合わせ(検出、運行情報、遅れ、駅名の引き当て)は、すべて10件ずつに分ける(`ODPTQuery.chunks`)。値がなければ問い合わせない
- 失敗したら、その段階で中止し、「◯◯が取れなかったため、検出を中止しました」と、URL(トークンを除く)・応答の本文を表示する
- 駅名の引き当て(行先の駅名)も、10件を超えると 400 になり、黙って駅IDの末尾の表示になっていた(v0.9.12 以前から)。同じ修正で直る

### v0.9.12 で追加したもの(ODPTの事業者の自動検出)

- トークンを保存したとき(と「再検出」)に、そのトークンで使える事業者・路線と、路線ごとに使えるデータ(運行情報/列車ごとの時刻表/駅の時刻表/遅れ/駅の位置)を10リクエスト前後で調べ、30日間保存する(`OperatorDiscoveryStore`、`OperatorDetection`)。コードに事業者を書き足さなくてよい
- チャレンジ限定ライセンスの事業者と、使えるデータがない事業者は除外し、登録の画面に理由を出す
- 登録の画面を「事業者(使えるデータのラベル)→ 路線(色、検索)→ 駅と方面」に。時刻表のない路線は「運行情報のみ登録」
- 既存の機能(地図・路線図・列車の位置・遅れ・乗車中の判定・駅に重ねる電車・駅の時刻表・経路の検索・デバッグ)は、事業者に依存しない作りのまま、検出した事業者の路線にも広がる。事業者をまたぐ経路のため、駅の一覧に、列車ごとの時刻表がある検出済みの事業者の駅を入れる
- 線路の形に、東京メトロ10路線・横浜市営地下鉄2路線・つくばエクスプレス・りんかい線・多摩モノレール・ゆりかもめを追加(N02 の駅で作成。22路線、約45KB)
- check_local.py で、フィクスチャのトークンらしき文字列と、Git の管理下のファイルの acl:consumerKey の値、private/ が管理外かを確かめる

## 実装済みの機能(1行ずつ)

- ホーム: 各機能の要約のカード。並べ替えと表示・非表示(非表示のカードのデータは取得せず、センサーも動かさない)
- 天気: Open-Meteo(現在、24時間、7日、日の出入り、UV)。現在地の地名。1リクエスト
- 雨の要約: 0〜60分は気象庁のナウキャスト、その先は予報モデル
- 雨雲レーダー: 気象庁のナウキャストのタイルを地図に重ねる(専用画面でだけ通信)
- 警報・注意報: 気象庁の新形式(r8)。市区町村は同梱の表で決定。ホームと天気タブ
- 地震: P2P地震情報。一覧、ホームのカード、詳細画面(津波、震源までの方角と距離、地図、各地の震度)
- 観測点ごとの震度の地図: 気象庁の観測点の一覧を同梱し、1枚の重ね描きで色分け
- 気圧: 実測(5分ごと、7日保存)と予報を1本の線に。ホームのカード、天気タブの節、詳細画面(過去4日〜16日先、Canvas の自前描画、タップで値)
- バックグラウンドでの気圧の記録(オプション、無音のオーディオ)
- 為替: 日次レート(JPY基準)と、オフラインの換算
- 移動(v0.9.9 で電車タブから作り直し): 地図中心の3段の画面(切り替え/地図・路線図・記録/情報と設定)。運行情報、駅の時刻表(手動で一度だけ保存)、路線の地図と路線図、時刻表から計算した列車位置と、リアルタイムの遅れ。v0.9.12 から、トークンで使える事業者を自動で検出して広げる
- ODPTの事業者の自動検出(v0.9.12): トークンの保存と「再検出」で、使える事業者・路線・データの種類を調べて30日保存。登録の画面は検出した事業者だけ(使えるデータのラベル、路線の色と検索)
- 乗車中の判定: 移動タブの表示中の位置から、線路に沿った動きを見て、時刻表の列車と照合。GPSが途切れたら時刻表で推定。移動の記録(保存期間を選べる、GPXで書き出し)
- 位置のデバッグ(開発者向け): 地図に引いた線・路線に沿った経路・GPXで、仮想の位置を動かして判定を試す(速さ、時間の倍率、停車、GPSなしの区間、ばらつき、仮想の時刻)。v0.9.10 から、選んだ経路の列車に時刻表どおりに乗って動くこともできる
- 駅に重ねる電車(v0.9.10): 拡大した地図で、駅の点のまわりに停車中と3分以内に着く電車。タップで列車の詳細(停車駅と到着予定、番線)
- 駅の時刻表と「間に合う」(v0.9.10): どの駅でも、保存した列車ごとの時刻表から方面ごとの時刻表を作る。遅れの反映、始発・終電、番線(一部の駅だけ)。今の場所から歩いて間に合うかの3段階
- 移動タブの画面の構成(v0.9.11): 切り替えを上端に固定し、地図と情報と設定を1つの縦スクロールに。地図の上の指は地図、外はスクロール。「地図へ」のボタン
- 線路の形(v0.9.11): 国土数値情報(鉄道データ)を加工して同梱(v0.9.12 で22路線)。地図の線、列車の位置、乗車中の判定、デバッグ、経路の線を、実際の線路の形に切り替え
- 行きたい駅までの経路(v0.9.10): 保存した時刻表だけで、接続を順に調べる方式で探す(乗り換え最大3回、6時間以内)。足りない路線の時刻表の取得、選んだ経路の地図の表示、「予定どおり」、降りる駅の1駅前の通知
- 地図: Wi-Fi では Apple Maps、それ以外では保存済みの地理院タイル。タイルの自動保存
- センサー: 速度(GPS、歩行ペースで補完)、歩数、気圧、傾き、騒音など。表示中だけ動作
- スコープ(以前のウェイポイント): 地点(登録、カメラ越しの印、コンパス)/ 周辺(MapKit で施設を検索)/ 経路(徒歩の経路、地図での案内、カメラ表示にも切り替え)
- 小ツール: 検索、お気に入り、ホームのカード。内蔵24個(タイマーとストップウォッチを含む)。トーナメント表は山型の表、ルーレット・サイコロ・コイントス・あみだくじは絵とアニメーション。JSONで読み込むツール(計算型・リスト型・表型・チェックリスト型、専用の式の評価器)
- 設定: タブの並び順、受信量(回線別・機能別)、自動更新の方針、地図の保存、登録内容、開発者向け(運行情報の直近の応答、カメラの起動時間)
- 配布: GitHub Actions で署名なしの ipa を作り、Releases と apps.json(LiveContainer の Sources 用)を自動更新

## 未着手の予定

- ODPT のトークンは利用者が持っていて、開発側(Claude)には渡さない。トークンを使う確認は、利用者が手元で行う。トークンはコード・リポジトリ・フィクスチャ・会話に書かない

  - アプリの検出と同じ手順で確かめるスクリプトが private/odpt_survey_detect.py(トークンなしの `--public` でも動く)。結果は private/odpt/detect.json
- 線路の形を ODPT の駅で作り直す(任意): 利用者が環境変数 ODPT_TOKEN を設定して `python scripts/update_railway_shapes.py TokyoMetro YokohamaMunicipal MIR TWR TamaMonorail Yurikamome` を実行すると、駅の順に沿った線になり、駅と線路のずれも表示される(今は N02 の駅で作ってある)
- 東京メトロ・つくばエクスプレス・りんかい線・多摩モノレールの列車ごとの遅れは、odpt:Train ではなく GTFS-RT(Protocol Buffers)でだけ提供されている(ckan.odpt.org のデータセットで確認)。使うなら、外部ライブラリなしで Protocol Buffers を読む処理が要る
- 遅延時の運行情報の実サンプルが手に入ったら: status の判定の検証
- それ以外のアイデアと、見送った案の調査結果: **private/ideas.md を参照**(Git の管理外。このPCの中だけにある。中身を CLAUDE.md や docs に書き写さない)

## コードを読んだだけでは分からない設計判断と、その理由

- **名前を変えても、内部の値は変えない**: `AppTab.waypoint`、`HomeCardKind.waypoint`、`waypoints.json`、型 `Waypoint`、設定キー `waypoint.showsHeading` は、表示名が「スコープ」「地点」になったあとも以前のまま。保存済みのデータと設定を引き継ぐため。同じ理由で、以前の「タイマー」のタブは、保存済みの並びの中で「小ツール」に読み替える
- **気圧の詳細画面と、観測点の地図は、あえて標準の部品を使っていない**: Swift Charts と MapKit のピンは、部品の数が数千になると iPhone SE 第2世代で重かった(実機の報告)。1枚の Canvas / 1枚の重ね描きで描き、スクロール中は描き直さない。スクロール位置を View の状態に入れないのも同じ理由
- **列車の位置は、リアルタイムの在線位置を使わず、時刻表から計算する**: 利用者の指定。リアルタイムのデータから使うのは遅れ(秒)だけ
- **カメラ越しの表示は ARKit を使わない**: 利用者の指定。回転行列から画面上の位置を計算する。ARで道路に帯を描く案は、調査のうえで見送り(記録は private/ideas.md)。経路は地図の案内が中心
- **カメラのセッションはアプリ全体で1つを使い回す**: 画面ごとに作り直すと、開くたびに設定のやり直しで遅かった
- **気圧の予報の補正は、全体を同じ量だけずらす**: 予報は地表の気圧で、端末のある高さとの差はほぼ一定だから。50km以上離れた地点に変わったら、保存した予報を捨てる(別の地点の値とはつなげない)
- **過去の気圧を100日分持つ案はやめた**: 利用者が見たいのは予報。過去は4日分の表示、7日分の保存に縮小した(Historical Forecast API も使わなくなった)
- **線路の形は、OpenStreetMap ではなく国土数値情報(N02)を使う**: N02 は国の公開データで、2020年度以降の版は CC BY 4.0(出典の表記と、加工したことの明記で、加工・同梱できる)。1路線が1本の中心線で、運営会社と路線名の属性があるので、ODPT の路線と対応付けやすい。OpenStreetMap(ODbL)は線路の本数ごとに線が分かれ、1本にまとめる手間が大きく、抜き出したデータを同梱すると、その部分を ODbL で公開する義務(継承)が生じうる。N02 の精度は2万5千分の1の地図が元で、駅とのずれは都営でおおむね数m〜数十m(一番大きいのは大江戸線の最初の都庁前で約70m)
- **移動タブの画面は、List の中に地図を置き、切り替えのボタンは List の外(上)に置く**: 固定の見出しを List の中で作ると insetGrouped では上端に残らないため。List の中の地図は、画面の外に出ると作り直されることがあるので、表示範囲を覚えて開き直す
- **駅を線路に合わせるときは「谷」のうち一番手前を選ぶ**(`GeoPath.snap`): 駅の順に、前の駅より先の区間で、線に沿って近づいて離れる所(谷)を候補にし、一番近い谷から100m以内のうち一番手前のもの。単に一番近い点を選ぶと、大江戸線の環状部のように線が近くを2回通る所で先へ飛び、その後の駅がすべてずれた(作るときに実際に起きた)。谷に絞らないと、直線の区間でも手前の点を選んでしまう。スクリプト(`check_stations`)とアプリで同じ規則にしてある
- **路線の線は TrainStore で1か所で作り置きする**(`rideLines()` / `rideLine(for:)`): 地図の線、列車の位置、判定、デバッグ、経路の線で同じ線を使わないと、列車が線路から外れて見えたり、判定の位置と地図がずれたりするため
- **地図は北が上のままで、回転させない(移動タブ)**: 列車の矢印の向きを、地図の回転に合わせて直していないため。回転を入れるなら、`TrainAnnotationView` の向きから地図の向きを引く必要がある
- **地図に触れている間は外側の List のスクロールを止める**(`ParentScrollLockRecognizer`): MKMapView を List の行に入れると、縦になぞったときに地図と画面のどちらが動くかが定まらない。自分では何も認識しない(ほかのジェスチャーの邪魔をしない)認識器で、触れたときに止め、離れたら戻す
- **列車の運行のIDは、列車番号・カレンダー・運行日で作る**(`TrainPositionCalculator.tripID`): 列車番号は毎日同じなので、番号だけでは日をまたぐと別の運行と区別できない。経路の区間(`JourneyLeg.tripID`)と、時刻表から計算した列車の位置(`TrainPosition.id`)を同じ形にして、「予定どおり」を比べる
- **駅の時刻表は odpt:StationTimetable ではなく、保存した列車ごとの時刻表から作る**: 登録していない駅でも、追加の通信なしで出せるため。遅れ(列車番号→秒)は、列車番号が毎日同じなので、今の前後3時間の電車にだけ反映する
- **経路の検索は6時間以内、乗り換えは3回まで**: 深夜に探したときに始発まで届くように6時間にした(0時半に探すと、6時半までの電車)。乗り換えの時間は設定の値に、150mより離れた駅どうし(蔵前、三田など)は歩く時間を足す
- **経路の最初の電車の「間に合う」は、出発の駅が現在地から3km以内のときだけ**: それより遠い駅は、今そこへ向かう前提ではない(予定を調べているだけ)と考え、今の時刻から探す。3km以内なら、急いで駅に着ける時刻から探す
- **経路の検索のために足した路線は、登録した路線とは別に持つ**(`TrainStore.routeRailways`): 運行情報や駅の登録を増やさず、地図の線と列車ごとの時刻表だけを保存する。設定の「経路の検索用の路線」で消せる
- **降りる駅の通知は、移動タブを表示している間だけ**: 位置の記録と判定がフォアグラウンドだけなので(バックグラウンドの位置情報は使わない)
- **経路の検索は、保存した時刻表だけで行い、外部の経路検索APIを使わない**: 通信量を最小にする方針のため。使えるのは列車ごとの時刻表がある事業者の路線だけ。v0.9.12 から、検出した事業者の駅も駅の一覧に入れて、事業者をまたいで探す
- **事業者の検出は、データを丸ごと取らず、確かめるための最小の問い合わせにする**(v0.9.12): 列車ごとの時刻表は1路線で100KBを超えるので、「列車のIDを1つ得て、その列車の時刻表を1件だけ取る」で有無を確かめる。列車のIDは、走っている列車(odpt:Train)か、駅時刻表1つから得る。駅時刻表の有無と駅の位置は、各路線の最初の駅の odpt:Station だけで分かる。どの問い合わせも、複数の事業者・IDをカンマ区切りで1回にまとめる
- **遅れが取れるかは、昼間に列車が1本もない事業者だけ「なし」と判断する**: 深夜は走っていないだけのことがあるので、未確認にして、遅れの取得を試す(取得の結果で「なし」になる)
- **チャレンジ限定の事業者は、コードの一覧(`OperatorCatalog.challengeOnly`)で外す**: ckan.odpt.org の API は公開されていない(/api/3/action は /dataset にリダイレクトされる)ので、アプリがライセンスを調べることはできない。ライセンスが変わったら一覧を直す
- **検出の結果は、キャッシュの削除では消さない**: 登録した路線の事業者のエンドポイントや、使えるデータを引くのに使うため。見つからない事業者は、トークンが必要な事業者として扱う(`OperatorDirectory.resolve`)
- **トークンがないとき・無効なときも、公開エンドポイントで検出する**: 都営は公開エンドポイントのまま使う(上書きの定義)。公開エンドポイントに事業者が増えても、コードを変えずに出る
- **線路の形の、N02 の駅で作るモード**: 開発側にはトークンがないので、トークンが必要な事業者は N02 の駅だけで線を作った。線の向きは駅の順と合わないことがあるので、アプリが最初と最後の駅の位置で向きをそろえる(`RideLine.oriented`)
- **乗り換えは odpt:connectingStation を使う**: 駅IDまで分かり、名前の違う乗り換え(東日本橋と馬喰横山、西巣鴨と新庚申塚)も取れる。都営では、同じ名前の都営の駅どうしはすべて書かれていた(2026-09-28に確認)。書かれていない事業者のために、同じ名前で500m以内の駅も乗り換えとみなす
- **経路は、着く時刻を変えずに途中の列車をできるだけ遅くする**: 接続を順に調べる方式は、同じ時刻に着く経路のうち、最初に見つかった(早く出る)ものを返すため。乗り換えで長く待つ経路になりやすい
- **駅に重ねる電車は、アノテーションではなく1枚の重ね描き**: 数が多いときに iPhone SE 第2世代で重くならないように。タップは部品に頼らず、アイコンの位置を計算して判定する
- **経路の検索のために足した路線の遅れは取らない**: 遅れの取得は、登録した路線だけ(`TrainStore.registeredRailways`)。足した路線は時刻表どおりとして扱う(通信量を増やさないため)
- **乗車中の判定は、時刻表の列車との照合で行い、リアルタイムの在線位置は使わない**: 列車の位置と同じ方針。判定のための通信はない
- **移動の記録はバックグラウンドで続けない**: 位置のバックグラウンドモードは、LiveContainer で Info.plist が効かないときに allowsBackgroundLocationUpdates を設定すると例外で落ちるため。気圧の無音再生でアプリが起きていても、フォアグラウンドの許可(使用中のみ)だけでは位置の更新は止まる
- **並行する道路の対策は、駅以外での停止と、線までの距離**: 速さだけでは電車と車を区別できない。止まる場所(駅かどうか)が一番の手がかりで、駅以外で25秒以上止まったら判定をやり直し、次は駅での停止を見るまで判定を出さない。信号の少ない道路を止まらずに走る車は、線に近ければ「確からしさ 低」で判定が出ることがある
- **デバッグの仮想の移動は記録に残さない**: 実際の移動の記録と取り違えないため。仮想の移動の間は、実際の現在地を地図に出さず、上部に赤い帯を出す
- **トーナメント表は、試合ごとの部品を作らず、1枚の Canvas に描く**: 64人で63試合・126個のボタンになるのを避けるため(気圧のグラフ、観測点の地図と同じ考え方)。タップは配置のロジックから判定する。Canvas の中では文字の省略(lineLimit)が使えないので、名前は文字の幅(全角2、半角1)で切る
- **メトロノームは、オーディオのセッションを非アクティブにしない**: 気圧の無音再生と同じセッションを共有しているので、止めるときに非アクティブにすると、無音再生まで止まる
- **割り勘・割引・消費税は、先に小数第3位で丸めてから円未満を処理する**: 2進数の誤差で1円ずれるのを防ぐため
- **Open-Meteo に models=jma_seamless を指定しない**: 指定すると降水確率と UV が null になる
- **JSONのツールは、プログラムを実行しない形式にした**: 他人が作ったものを読み込む前提なので、通信や端末のデータに触れる項目を形式に持たせず、式も専用の評価器(上限つき)で処理する
- **テストしたいロジックは View の外に置く**: View に準拠した型は全体が `@MainActor` になり、テストから呼びにくい。`@MainActor` なクラスの静的メンバーも同じ(`nonisolated static` にするか、定数を別の enum に出す)
- **ファイルのパッチは、Pythonのスクリプトをファイルに書いてから実行する**: bash のヒアドキュメントに Swift や JSON の文字列を入れると、引用符で壊れることがある。Swift のファイルを直接書くときは、`\(` や `\.` のバックスラッシュを二重にしない(check_local.py が検出する)
- **ドキュメントの更新は ci の前に同じ push に入れ、ci が成功したコミットにタグを付ける**: release.yml はテストをしないため

## 作業の進め方(要点)

- 詳細は CLAUDE.md の「ビルドと検証」。push と ci は区切りごとに1回だけ(`gh workflow run ci.yml --ref main`)。その前に `python scripts/check_local.py` を通す
- ci は通常4〜5分。**v0.9.7 で約11分、v0.9.11 で約16分かかった(原因は未特定)**。v0.9.7 のときは、テスト自体はミリ秒、実機向けのコンパイルは51秒で、長かったのはシミュレーターでのビルドとテストの段階。v0.9.11 もその段階(「ビルドとテスト(iOSシミュレーター)」)で長かった。どちらも失敗はしていない。調べるなら、ci のログでシミュレーターの起動とビルドの各段階の時刻を比べる(macOS の runner の混み具合、シミュレーターの起動待ち、ビルドのキャッシュがないこと、などが候補)。調べるための ci の実行も回数に数える
- リリース後は、apps.json が main に反映されたことを確かめる(`git show origin/main:apps.json`)。raw のURLは最大5分キャッシュされる
- `private/` は `.git/info/exclude` で管理外にしてある(クローンし直したら、同じ1行を足す)
